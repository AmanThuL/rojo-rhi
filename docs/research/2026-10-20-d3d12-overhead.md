# The D3D12 backend's overhead against native code

**Status**: Proposed (until the first timed D3D12 round on the Windows GPU PC)

This note is the T2 benchmark round for the D3D12 backend: the measurement suite of
[ADR 0014](../decisions/0014-overhead-measurement.md), run against hand-written D3D12 code, to the
budgets that ADR fixes. It is the D3D12 twin of [the Metal 4 pre-registration](
2026-10-18-metal4-overhead.md), as amended for [round 2](2026-10-20-metal4-overhead-round2.md): it
adopts by reference everything there that does not depend on the backend and states every D3D12
difference below. It is the round's pre-registration. It becomes binding at the first timed run on
the Windows GPU PC; before that it changes only through a dated entry under Amendments, and after
it, changing the workloads, metrics, statistics or decision rules invalidates the round. The
results section is filled in when the round reports; a later round is a new note.

WARP, the software adapter, runs the round's correctness gate on hosted CI and nothing else: a WARP
run is correctness evidence, never a measurement, never a cost and never T1 acceptance
([documentation](../conventions/documentation.md)). The harness's D3D12 arms, the backend's
GPU-timing seam, the driver's d3d12 options and the CI gate arrive with the work that builds them
([the harness](../architecture/benchmarks.md)); this note fixes what they measure. No sentence here
reports a D3D12 measurement.

## Question

Does RojoRHI on D3D12 stay within ADR 0014's budgets against the best hand-written D3D12 code for
the same workloads?

| Metric | Budget (ADR 0014) | Judged here as |
|---|---|---|
| CPU tax per operation over native | at most 5% | C1 to C10 at `K` of 100 and above |
| GPU frame-time tax over native, composed frame | at most 1% | the composed frame only |
| Hidden pipeline variants | zero | no pipeline created after warm-up |
| Per-frame heap allocations after warm-up | zero | R allocates no more per frame than N, counting the C++ allocations of both arms (metric 3) |
| Native calls per RojoRHI call on hot paths | at most the native minimum plus one | an operation of `c` RojoRHI calls makes at most N's count plus `c` |

## Arms

| Arm | What runs |
|---|---|
| N, native | D3D12 code written for the workload, on a device made through the Agility SDK's own `ID3D12SDKConfiguration1::CreateDeviceFactory` (SDK version 619, the `D3D12\` directory beside the executable), the method the backend uses ([the D3D12 backend](../architecture/d3d12-backend.md)): the fewest native calls that do its work, with the same resources and frame pacing a careful renderer uses, and the same shaders as R: the DXIL the pinned Slang emits for the sources in `Shaders/Bench/`, except G1 and G2, whose N kernels are hand-written HLSL compiled by the pinned DXC |
| R, RojoRHI | the same workload through `RHI.h` on the `d3d12` backend, in a Release build with link-time optimization, shaders compiled from Slang through the module, and the Metal note's fixed `DeviceDesc`: `framesInFlight` 3, `validation` false, `enableCapture` false, an empty `pipelineCache` |

Both arms live in one benchmark executable and run on the same adapter: N selects it with the
backend's rule (`EnumWarpAdapter` on a WARP build, otherwise the first high-performance adapter that
meets the hardware floor), and the run records N's adapter description, LUID and driver version.
Both run three frames in flight. The Slang DXIL reads the global root signature's layout (a root
SRV at `t0` with `DATA_VOLATILE`, one root constant at `b1`, both heaps directly indexed), so N
creates a root signature of that layout for those shaders, and G1's and G2's hand-written kernels
take their own. N follows the API reference's D3D12 mappings where they are the native minimum and
departs from them where native code does less; each workload states its departures, `none` when
it has none.

## Workloads

The Metal note's workloads, `K` sweeps and `c` apply unchanged: the CPU operations C1 to C10 with
their passes, targets and repetitions, the kernels G1 and G2, the composed frame with its resources,
passes, barrier batches and five submissions, and every sweep limit. N's column for D3D12 lists its
native calls per repetition.

| Id | `c` | N per repetition | Departures |
|---|---|---|---|
| C1 | 3 | `memcpy` of the 64-byte block into N's persistently mapped upload arena, then `SetGraphicsRootShaderResourceView` and `DrawInstanced`: 2 calls | none |
| C2 | 3 | as C1 with `DrawIndexedInstanced`: `SetGraphicsRootShaderResourceView`, `DrawIndexedInstanced`, 2 calls; `IASetIndexBuffer` once before the repetitions | none |
| C3 | 2 | `SetPipelineState`, `DrawInstanced`: 2 calls | cull mode and depth-stencil state live in the pipeline state, and both pipelines share one topology, so N sets `IASetPrimitiveTopology` once before the repetitions, where chapter 06 resets the topology at every `setPipeline` |
| C4 | 3 | arena `memcpy`, `SetComputeRootShaderResourceView`, `Dispatch`: 2 calls | none |
| C5 | 1 | arena `memcpy`: 0 calls | none |
| C6 | 2 | `Dispatch`, one `ID3D12GraphicsCommandList7::Barrier` with one `D3D12_GLOBAL_BARRIER`: 2 calls | none |
| C7 | 1 | `CopyBufferRegion`: 1 call | none |
| C8 | 7 | the 8 calls listed below (7 in the first pass) | N sets the pipeline, topology, viewport and scissor once before the first pass, where chapter 06 writes the starting state at every `beginRenderPass` |
| C9 | 1 | `ExecuteCommandLists`, `Signal`: 2 calls | none |
| C10 | 1 | `ExecuteIndirect` with the draw command signature (a `D3D12_INDIRECT_ARGUMENT_TYPE_CONSTANT` argument into `b1`, then `D3D12_INDIRECT_ARGUMENT_TYPE_DRAW`, stride 20), `MaxCommandCount` 256 and the count buffer: 1 call per counted draw | none |

C8's sequence, in order: `Barrier` with one `D3D12_TEXTURE_BARRIER` on the target (none before the
first pass), `BeginEvent`, `EndQuery` of a `D3D12_QUERY_TYPE_TIMESTAMP`, `BeginRenderPass`,
`DrawInstanced`, `EndRenderPass`, `EndQuery`, `EndEvent`: 8 calls. The barrier is the lowering
[chapter 09](../spec/09-synchronization-part2.md) gives R's `TextureBarrier`, from
`D3D12_BARRIER_SYNC_RENDER_TARGET` and `D3D12_BARRIER_ACCESS_RENDER_TARGET` to the same, the layout
staying `D3D12_BARRIER_LAYOUT_RENDER_TARGET`. Pipeline state, topology, viewport and scissor
persist across render passes on one command list
([chapter 06](../spec/06-pipelines-part2.md)), so N sets them before the first pass only. N mirrors
the profiling markers R's pass scope emits, the event pair and the two timestamps, as the Metal
round does, and resolves its timestamps with one `ResolveQueryData` per frame, outside the
repetitions. C8 runs `K` up to 10,000 as on Metal. The Metal reasons, an encoder limit and the
counter heaps a process may hold, do not apply to D3D12, where one query heap holds the 20,000
timestamps of `K` 10,000; keeping the sweep keeps the two rounds comparable.

C10's records and count are the same `Gpu` buffers in both arms; R looks up each `Addr`'s resource
and offset from its heap index while recording ([chapter 08](../spec/08-gpu-driven.md)), which is
R's CPU time and no native call. The Metal round's C10 departures (hand-written encoding kernels,
`Shared` buffers, indirect command buffers sized to `maxCount`) do not exist here, since D3D12
draws a counted draw natively. C10 at `maxCount` 1 with a null count stays a report-only row: N's
`ExecuteIndirect` with `MaxCommandCount` 1 and no count buffer, 1 call; on D3D12 the records keep
their layout through the command signature at no extra call. C10 keeps `K` up to 1,000, so the
two rounds stay comparable, although the Metal reason, the size of its indirect command buffers,
does not apply on D3D12.

**GPU kernels**, report-only:

| Id | N | Departures |
|---|---|---|
| G1 | the 16 `uint4` loads through a root SRV, a GPU virtual address set by `SetComputeRootShaderResourceView`, with no descriptor fetch | N reads with no descriptor fetch where R's `Addr` costs one per base ([chapter 05](../spec/05-shader-abi-part2.md#addresses)), so on D3D12 G1 reports, at the module level, what [spike 1](2026-10-20-spike-1-d3d12-addr-dereference.md) measures |
| G2 | arm T reads the 128 textures and the sampler through `ResourceDescriptorHeap` and `SamplerDescriptorHeap` indices from the root, as R's lowering does; arm F, for the record, through a 128-entry SRV descriptor table and a static point sampler (`D3D12_FILTER_MIN_MAG_MIP_POINT`) | F uses a descriptor table and a static sampler, which the reference's global root signature does not have |

**Composed frame.** The frame of the Metal note, with its 14 passes, barrier batches, lists, fences
and five submissions, each submission one `ExecuteCommandLists` with the `Wait` and `Signal` calls
its row names. N lowers each barrier batch as chapter 09's D3D12 column lowers R's: one
`ID3D12GraphicsCommandList7::Barrier` call per non-empty batch, with one `D3D12_BARRIER_GROUP` per
non-empty kind, enhanced-barrier layouts as R's batch states them, and `Undefined` adding
`D3D12_TEXTURE_BARRIER_FLAG_DISCARD`. Two consequences differ from Metal: a batch whose source stage
is `None` still makes a call, since the texture changes layout, and the closing batches of the
`gbuffer` and `ao` lists are recorded as calls where they stand, because D3D12 carries no barrier
past a list's end. Each counted draw is `IASetIndexBuffer` and one `ExecuteIndirect` with the
indexed command signature (the constant into `b1`, then `D3D12_INDIRECT_ARGUMENT_TYPE_DRAW_INDEXED`,
stride 24) and the view's count; pass 8's 500 boxes are each `SetGraphicsRootShaderResourceView`
and `DrawIndexedInstanced`. Both arms label every list and pass, and write an event pair and a pair
of timestamps per pass, as the Metal note registers. Departures: none.

## Metrics

1. **Correctness gate.** As the Metal note's, R against N byte for byte for every workload and
   configuration. Each configuration also runs in Release without validation, and in Debug with
   `DeviceDesc::validation` for R and the D3D12 debug layer in both arms (no GPU-based validation),
   enabled on each arm's own device factory. Neither arm may report a message: N's
   `ID3D12InfoQueue1` callback writes each corruption, error and warning to standard error, denying
   only the messages the backend's deny list denies for the same reasons, and any line on standard
   error fails the configuration. A workload failing the gate is not timed.
2. **Native calls.** A native call is a call on an `ID3D12Device*`, an `ID3D12CommandQueue`, an
   `ID3D12GraphicsCommandList*`, an `ID3D12Fence`, a query heap or a descriptor heap, and
   `ID3D12Resource::Map` and `Unmap`; filling a descriptor, a barrier group or a pipeline stream
   struct is not. `Reset` of a command allocator and of a list counts as a host call outside every
   per-operation window, as on Metal. R's count comes from `Device::counters`, N's from a plain
   increment beside each call site. The count per operation is the Metal note's `K` pair
   difference: `(count at K = 1,000 - count at K = 100) / 900`, and for C9 `(count at K = 100 -
   count at K = 10) / 90`. Exact.
3. **Allocations.** Every C++ allocation of the process, counted by replacing the global
   `operator new` and `operator delete` in every form, during the measured frames of R and of N.
   This departs from the Metal note, whose malloc-zone counter also saw Metal's allocations: the
   D3D12 runtime's and the driver's heap allocations do not pass through `operator new`, and a
   direct `malloc` or `HeapAlloc` call is not seen in either arm. The rule stays R at most N, so on
   D3D12 it judges RojoRHI's own allocations against N's. R's `cpuAllocations` is reported beside
   it.
4. **Pipelines.** Unchanged: `pipelinesCreated` and `nativeCreateCalls` after warm-up. Exact.
5. **CPU time.** `QueryPerformanceCounter`, of resolution `1 / QueryPerformanceFrequency` on the
   machine, recorded per run. R's span runs from list acquisition to `end`; N's from the command
   list's `Reset` to its `Close`, the allocator's `Reset` falling outside it; for C9, the submit
   calls only. Per operation, the span divided by `K`.
6. **GPU time.** Timestamps at the start of a submission's first list and at the end of its last:
   R through the backend's test-only seam, which writes an `EndQuery` of a timestamp first and last
   in every list of a queue it is attached to, then resolves them, and N writing the same pair in
   its own lists. Every registered submission holds one list, so both arms pay the same two
   timestamp writes and one `ResolveQueryData` per list, counted nowhere. In both arms ticks become
   seconds through each queue's `GetTimestampFrequency` and its `GetClockCalibration` pair, both
   taken when timing attaches, so the graphics and compute queues share the CPU's clock. The
   composed frame's GPU time is the span from the earliest start of its five submissions to the
   latest end, across both queues; G1 and G2 use their single submission's span. No time is summed
   over lists.

## Statistics

The Metal note's, with these differences:

- Release builds with link-time optimization, configured with `--rojorhi_d3d12_debug=mode`, which
  enables nothing in Release; validation off for timed runs and on for the correctness runs.
- Each repetition is one fresh process for one workload and `K` that runs both arms, R first in
  even processes and N first in odd ones; 20 processes per configuration, interleaved across the
  configurations of a workload, on AC power. Per process and arm, 50 warm-up and 200 measured
  frames, each submitted and waited to completion; the process median is kept and the reported
  value is the median of process medians.
- Paired deltas R minus N within a process; two-sided 95% percentile bootstrap intervals with
  10,000 resamples over processes, seed 20261021.
- Recorded per run: the GPU with its vendor and device id, the driver version, the Windows build,
  hardware-accelerated GPU scheduling, the Agility SDK and WARP file versions (WARP unused for
  timing), the DXC, Slang and MSVC versions, the repository commit and the power source.
- Thermal control: Windows has no thermal state, so the harness reports `"unknown"` and no process
  is discarded on it. Instead, before and after each timed process `bench.py` reads `nvidia-smi
  --query-gpu=temperature.gpu,clocks.sm --format=csv,noheader,nounits` when it exists: a process
  whose end temperature exceeds its start by more than 10 °C, or whose end clock is below 95% of the
  round's median start clock, is discarded (`.discarded<k>.json`) and rerun after 120 s, at most 4
  attempts, then reported not run. Without a vendor command-line tool the round records `thermal:
  not monitored` and sleeps 30 s between processes.

## Decision rules

The Metal note's, with the backend being D3D12:

- **CPU.** A configuration at `K` of 100 or above misses the CPU budget when the interval of R
  minus N excludes zero and the median delta exceeds 5% of N's median; smaller `K` are reported.
  C10 is judged on CPU time against N's `ExecuteIndirect`, and its call count is reported, not
  judged, as on Metal: the count rule covers C1 to C9 in both rounds so that they are judged alike,
  although the reference marks a counted draw `cheap` on D3D12 where it marks it `costly` on
  Metal 4 ([cost summary](../spec/A-cost-summary.md)). C10 at `maxCount` 1 is reported only.
- **GPU.** The composed frame misses the GPU budget when the interval of its frame-time delta
  excludes zero and the median delta exceeds 1% of N's. G1 and G2 are reported only.
- **Counts.** Any operation of C1 to C9 whose native calls exceed N's count plus its `c`, any
  workload whose R allocations per frame, as the median of process values, exceed N's in any of
  its configurations, or any pipeline created after warm-up, misses the budget. A count that
  differs between frames or processes is reported unstable and judged on its maximum.
- **A miss** is a defect in the D3D12 backend: the backend is fixed and the round is run again as a
  new note. Heap indexing and `Addr` dereference on D3D12 are reopened, through
  [chapter 05's D3D12 rows](../spec/05-shader-abi-part2.md) and spike 1 (issue #20), only when the
  composed frame misses its GPU budget and investigation shows that they are the cause.
- The results change the API reference in the same change that records them where a mapping's
  stated cost was wrong.

## Procedure

- On the Windows GPU PC, from a clean checkout of the commit that merges this note or its last
  amendment, on AC power with the High-performance power plan, with nothing else built, tested or
  timed on the machine: `python3 Tools/bench.py --topic t2-d3d12 build --backend d3d12 --adapter
  hardware`, then `correctness`, `timing` and `analyze` under the same topic. Timing runs in
  Release with validation off.
- Never on hosted runners and never on WARP: `bench.py timing` refuses a build whose adapter is
  `warp` ([ADR 0014](../decisions/0014-overhead-measurement.md), "Where measurement runs").
- Raw logs, per-process results, `summary.json` and `analysis.txt` are kept in
  `rojo-rhi-evidence/t2-d3d12/<date>/` with a `SHA256SUMS` manifest
  ([GPU evidence](../guides/gpu-evidence.md)); this note keeps the environment, the summary tables
  and the decisions.
- Hosted CI runs the correctness gate, both arms in Release and Debug on WARP, in the `d3d12-bench`
  job under the `t2-gate-d3d12` topic. Its results are correctness evidence only.
